# Reference outputs

> ## Plan 9 — these stop being *Java* reference outputs
>
> **Read this before regenerating anything.** Plans 1-8 cut every file under this directory from
> the Java jar, and byte parity with the jar was the port's acceptance test. **Plan 9 reverses
> that.** The port fixes 121 catalogued defects, byte parity with the jar may break wherever a fix
> lands, and the evidence moves from "the jar agrees" to "the port's own golden did not move
> unexplained, and the routing got better on 605 real boards". From Plan 9 Task 1 on, everything
> here is **regenerated from the port** and is the port's own golden.
>
> ### The freeze
>
> Before the first regeneration, Task 1 copies this whole tree, as it stands at the last
> jar-generated commit, to the **sibling** directory
>
> ```
> tests/reference-frozen/java-head-2026-09/
> ```
>
> — a sibling, never a child of `tests/reference/`, because a recursive copy of a directory into
> itself is not expressible and because a child would be swept up by every glob that walks this
> tree. The freeze is a **historical artefact, not a test input**: it is written once, made
> read-only, and **read by nothing** — no test, no script, and specifically not
> `scripts/quality-ab.sh` (ruling BL8, as amended by ruling BP1). The jar's quality numbers are
> derived from it **once**, at Task 1, and written *outside* it to
> `benchmark/baselines/quality-baseline-java-head.tsv`, where the A/B harness reads them as
> context and never as a gate. `grep -rn "reference-frozen" crates/ scripts/` must return nothing
> but prose for the whole of Plan 9, and `tests/reference-frozen/README.md` says so at the other
> end.
>
> ### The two generator lanes
>
> Each of the five generators now takes a lane:
>
> | flag | drives | what it is for |
> |---|---|---|
> | `--jar` (**the default**) | the jar, exactly as before | the frozen baseline, and **triage**: when a port-cut golden churns for a reason nobody can name, this answers "did the jar move, did the port move, or did the reference?" |
> | `--from-port` | the port — its CLI, or its own `p6t1` / `p7t9` / `refwriter` twin | what regenerates the committed references from Task 1 on |
>
> A `--from-port` run writes three provenance lines into the stem's `meta.txt`: **the port's git
> sha, the Plan 9 task at that sha, and the `RouterBudget` in force**. That line exists so that a
> golden cut *before* a later fix is **loudly** invalid — a reader who finds `plan 9 task UNKNOWN`,
> or a task number older than the fix they are chasing, knows the reference is stale without
> having to re-derive it. Cut a reference without `--task T<n>` and the file says so in capitals.
>
> `REFERENCE_OUT_ROOT` redirects a generator's **output** to a scratch tree while it still reads
> the fixture tables from here — which is how a lane is proved byte-unchanged without moving a
> committed byte.
>
> ### What does not change
>
> The stem lists, the `-mp` caps, the file names and the meaning of every artefact are unchanged;
> so is the rule below that **no generated file is ever edited by hand**. The `--jar` lane still
> produces exactly the bytes it produced before Plan 9 — Task 0 proved that by re-running it into
> a scratch tree and diffing, and the Task 0 report records what was compared and the two known
> non-deterministic fields (a `drc.json` `date` stamp and a `route.log` timestamp) that no lane
> can make reproducible.
>
> Everything below this box describes the **jar** lane and is still accurate for it.

# Java reference outputs

Generated by `scripts/gen-reference.sh` from the pinned freerouting 2.3.0 jar
(the parity baseline per the Java repo's AGENTS.md). For each stem in
`fixtures.txt` the script produces:

- `<stem>/roundtrip.dsn` — Java `DsnReader.readBoard` → `DsnWriter.write`, no routing
- `<stem>/unrouted.ses`  — same board → `SesWriter.write`, no routing (0 `(wire` entries)
- `<stem>/java.log`      — driver output, for debugging

## How it works (and why not `-de/-do`)

The script compiles `scripts/gen-reference/RefWriter.java` against the jar and
runs it per fixture. The normal `-de/-do` job path was tried first and cannot
produce these references:

- `-do <file>.dsn` is accepted but the headless job writer only emits SES or
  KiCad JSON, so the DSN output is an empty file.
- `-mp 0` means *unlimited* passes, not zero.
- `--router.enabled=false` disables only the autoroute stage; fanout and the
  optimizer still run and modify the board (fanout added vias/wires).
- With all three of `--router.enabled=false --router.fanout.enabled=false
  --router.optimizer.enabled=false` the job completes with nothing to do and
  writes 0 bytes.

## Which fixtures, and why

`fixtures.txt` has seven stems. The first four (`tutorial_board`,
`Issue026-J2_reference`, `Issue103-Board-Unrouted`, `Issue143-rpi_splitter`)
are the plan's original bit-parity set. Between them they have **zero**
`polyline_path`, zero wiring `(via `, zero `(type shove_fixed|fix|protect)`
and zero `(plane ` — so they prove the `structure`/`placement`/`library`/
`part_library`/`network` writers and nothing about six others. Plan 3
controller ruling G added three more in Task 15 to close that:

| stem | exercises | roundtrip.dsn | wires in .ses |
|---|---|---|---|
| `Issue413-test` | 11 `polyline_path`, 4 wiring vias, 3 fixed states | 8,492 B | 11 |
| `Issue110-RelayModule` | 22 wiring vias, 22 fixed states | 171,349 B | 0 |
| `Issue753-CPU-85_r104` | 3 `(plane …)`, 65 `polyline_path` | 273,049 B | 0 |

`Issue413-test` is the only reference whose `unrouted.ses` carries `(wire`
entries, so it is the one that pins `SesWriter`'s trace path. The other six are
wire-free. Both halves of that are asserted: `parity_ses.rs`'s
`no_reference_contains_a_wire` runs over all six wire-free stems (the ruling-G
ones included) and `ruling_g_references_do_carry_wires` pins `Issue413-test`'s
11 entries.

**Never edit a generated file by hand** — regenerate with the script. Adding a
stem to `fixtures.txt` and re-running is the whole procedure; the script is
idempotent for the stems already present (only `java.log`'s timestamp changes).

Note the 2.3.0 jar's package layout predates the clone's renames
(`app.freerouting.board.BasicBoard`, not `board.facade`); the driver imports
the jar's names.

## Why the 2.3.0 jar, not the clone's HEAD (Plan 3 ruling 1)

The clone's HEAD camelCased fifteen Specctra keyword names in `Keyword.java`
*and* the writers' string literals (`(hostCad `, `(viaRule `, `(snapAngle `,
`(stringQuote `, ...), while its lexer still only recognises the snake_case
tokens -- so HEAD writes DSN it cannot read back (re-reading its own
`tutorial_board` output drops `host_cad`, every via rule, every clearance rule
and 26 wires). The 2.3.0 jar writes the correct Specctra tokens, and diffing
HEAD's output against these references differs in exactly those fifteen tokens
and nothing else on every fixture. The port therefore emits the 2.3.0 tokens,
these references are the acceptance target, and `docs/java-quirks.md` #92 is
the upstream bug report. Regenerating with a HEAD jar would silently move the
target; do not.

Reference files are committed. `_scratch/` holds the Rust side of a failing
comparison and is gitignored, as is `scripts/gen-reference/build/`.

Requirements: JDK 25 (`brew install openjdk@25`, then
`JAVA=/opt/homebrew/opt/openjdk@25/bin/java scripts/gen-reference.sh`), network
access on first run to download the jar into `tools/`.

# DRC references (`drc-*`, Plan 5 Task 9)

The seven stems above are `scripts/gen-reference.sh`'s. The eight `drc-*` stems are a **separate
set**, generated by `scripts/gen-drc-reference.sh` from a **different jar**, and listed in
`drc-fixtures.txt` (`stem|dsn|rules|ses`) rather than in `fixtures.txt`. Per stem:

- `<stem>/drc.json`     — the `-drc` CLI's report, **verbatim**
- `<stem>/drc.meta.txt` — the jar's identity (size, mtime, version), `java -version`, the hash
                          mode and the command line. Every machine-specific prefix is written as
                          `<FREEROUTING_JAVA_DIR>` or `<workspace>`, so the file is byte-identical
                          wherever it is regenerated. `scripts/gen-drc-reference.sh --meta-only`
                          rewrites it from the existing `drc.json` without running the jar, for
                          when this file's format changes and the references must not move
- `<stem>/java.log`     — the CLI's stdout+stderr. **Unlike the other two it is machine-specific**:
                          it carries absolute paths and wall-clock timestamps, exactly as
                          `gen-reference.sh`'s `java.log`s do. It is kept for debugging and read by
                          nothing, so a diff in it means nothing

## Why a second script and a second jar

`gen-reference.sh` is pinned to the downloaded **2.3.0** jar because the `io/specctra` byte-parity
references have to be 2.3.0's (Plan 3 ruling 10, "Why the 2.3.0 jar" above). The DRC references
have to be the clone's **HEAD** build: Plan 5 ports HEAD's `drc/**` and `io/kicad/KiCadDrc*.java`,
every file:line in that plan is HEAD's, and the two jars disagree about the report's key spelling
(HEAD writes `coordinateUnits`/`holeClearance`, 2.3.0 writes `coordinate_units`/`hole_clearance` —
plan-5 rulings 1 and 2). Putting two jars behind one `fixtures.txt` would hide that skew, so the
DRC set gets its own file, its own script and its own `drc-` stem prefix.

Unlike the DSN/SES case, no Java driver has to be compiled: `-drc` works from the CLI as-is, for a
plain DSN, for a DSN + `.rules` (`-dr`) and for a DSN + `.ses`. Driving the real CLI is also what
puts a real `qualityScore` in the reference — `DesignRulesChecker` alone never computes it
(`Freerouting.java:343-352`; plan-5 ruling 5 makes it an injected `Option<f64>` in the port, and
`crates/fr-drc/tests/reference_parity.rs` feeds the reference's own value back in).

**There is no `-ds` flag.** The session file has no option of its own: `GlobalSettings` collects
every non-`-` argument after `-de` into a slot list and sorts them by extension
(`GlobalSettings.java:564-648`), so the DSN and the SES are simply two arguments in the `-de` slot.
A single `<dsn>+<ses>` argument reaches the same list through the `+`-split at `:573-579`; the
generator uses the two-argument form, which needs no split and survives a path containing `+`.
(Verified equivalent: both forms produce a `drc-issue593-ses` report byte-identical to the
committed one apart from `date`.) `-drc` is matched by `startsWith` *before* `-dr` in the same
if-chain (`:660-674`), so the two flags cannot be confused whatever their order on the command
line.

## The hash-mode sweep, and the one stem that fails it

`scripts/gen-drc-reference.sh --verify-hash-modes` regenerates every stem once per
`-XX:+UnlockExperimentalVMOptions -XX:hashCode=0,1,2,3,4` and reports how many distinct
**normalised** documents (`scripts/normalize-drc.py`) come out. Agreement is what makes a
reference a property of the board rather than of the JVM run that produced it. Result on the jar
named in `drc.meta.txt`:

| stem | distinct normalised documents over the five modes |
|---|---|
| `drc-dev-board`, `drc-bbd-mars-64`, `drc-issue593-rules`, `drc-issue593-ses`, `drc-issue753-cpu85`, `drc-issue110-relay`, `drc-tutorial-board` | **1** |
| `drc-natural-tone-preamp` | **5** |

`drc-natural-tone-preamp` is recorded, not papered over. `generateReport` folds
`getAllUnconnectedItems`' `track_dangling` entries into `violations`
(`DesignRulesChecker.java:271-276`), and that phase's dedup (`:160`) drops whichever dangling trace
a net entry's hash-ordered `firstItem` happens to be — a representative-dependent result
(`findRepresentativeItem`, plan-5 ruling 3; quirk #146).

**Its violation count lands in the range 113-115, and only `-XX:hashCode=2` pins it.** Mode 2 is a
constant, so it is the one `Object.hashCode` source that reproduces run to run without being
derived from an object address; it gives **115**, and that is the committed reference. Modes 0 and
5 are PRNG-seeded and modes 1 and 4 are address-derived, so their counts move between sweeps — two
independent sweeps of this same jar agreed on mode 2 and disagreed with each other on modes 0 and 4
— and mode 3 is a per-thread xorshift, deterministic only within a single-threaded run. **No
per-mode count should be quoted for those four**; the honest statement is the range plus mode 2's
value. Three independent sweeps of this jar have now been taken (Task 9's, the reviewer's and a
re-run): every one of modes 0, 1, 3 and 4 produced a different count in at least one of them, and
mode 2 produced 115 in all three. `crates/fr-drc/tests/data/README.md` records the same finding
from Tasks 4, 7 and 8.

**All eight references are therefore generated under `-XX:hashCode=2`.** For the seven
hash-independent stems the flag changes nothing; for this one it is what makes the reference
reproducible at all. `references_are_from_the_head_jar` asserts every `drc.meta.txt` says so.

The port's own answer on that fixture is 112 violations — its ascending-id representatives make
three of the fixture's four `Trace`-represented net entries dangling — and
`natural_tone_preamp_is_the_reference_minus_three_dangling_tracks` requires the port's document to
be this reference with exactly the three `track_dangling` entries whose item uuids are `1909`,
`1696` and `1242` deleted **in place**, pinned by uuid rather than by count. The other 44
`unconnectedItems` entries and the remaining 112 violations are byte-identical.

## The normalisation is three lines long, on purpose

`parity::normalize_drc_json` drops `date` (`ZonedDateTime.now()`, `KiCadDrcReport.java:70`, an
injected string in the port) and sorts each `unconnectedItems` entry's `items` by **numeric** uuid
(on the JVM that array is two `HashSet<Item>`s, quirk #144). It does **not** touch `violations` —
neither the array order nor any entry's `items`, because a clearance entry's `items` is
`[firstItem, secondItem]` in a deterministic order and sorting it would hide a real ordering
regression. `scripts/normalize-drc.py` is the Python twin, used by `--verify-hash-modes` only; it
is deliberately not on the path of any committed byte, which is why the committed `drc.json` is the
jar's own output and the Rust normaliser is applied to *both* sides inside the test.

## The `*-freerouting_drc.json` files in the Java fixtures directory are NOT references

`../freerouting/fixtures/Issue575-*-freerouting_drc.json` look like DRC references and are not
(plan-5 ruling 10). Verified while writing this task:

- they are `Freerouting 2.1.2-SNAPSHOT`-era and carry **no `quality_score`** key at all;
- they are snake_case, i.e. neither jar's current output for two of the type strings;
- the dev-board one claims **5 violations / 1 unconnected item** where both current jars produce
  **10 / 4**; the BBD Mars-64 one claims 93 / 0 against 96 / 3, and the Natural Tone Preamp one
  28 / 9 against 113-115 / 44.

The `*-kicad_drc.json` files beside them are KiCad 9.0.1's own output and are the evidence for
ruling 2's `DrcJsonFlavor::KiCad` spelling, not a parity target either.

**Never edit a generated file by hand** — regenerate with
`scripts/gen-drc-reference.sh [stem ...]`. The one thing that changes on every regeneration is
`date` (and `java.log`'s timestamps); the parity test drops it on both sides.

# Router references (`router-*`, Plan 6 Task 17)

`tests/reference/router-<stem>/router.jsonl` is one JSON line per **routed
connection** — the third reference family in this directory, and the first that
is neither a whole file the jar wrote (`fixtures.txt`'s DSN/SES round trips) nor
a report it generated (`drc-fixtures.txt`'s `-drc` documents).

`scripts/gen-router-reference.sh` writes them from
`tests/reference/router-fixtures.txt` (`stem|dsn|max_items|ripup_pass_no`, paths
relative to the Java checkout; Plan 7 Task 16 made fields 3 and 4
mandatory-or-`-` and appended three batch columns at 5-7, which this script does
not read) and `crates/fr-router/tests/reference_parity.rs` reads the same table,
so the generator and the tests cannot drift apart. A row with `-` in `max_items`
is a batch-only row and this generator skips it.

## A third script, and the HEAD jar again

Like `gen-drc-reference.sh` this one is pinned to the clone's **HEAD** build, not
to the 2.3.0 jar the DSN/SES references need: HEAD's `autoroute/**` has been
refactored away from upstream (`MazeSearchAlgo` → `maze/MazeSearchEngine`,
`LocateFoundConnectionAlgo*` → `path/FoundConnectionLocator*`, and
`MazeExpansionEngine`/`MazeRipupResolver`/`AutorouteConnectionRouter` do not
exist there at all), so a 2.3.0 reference would be a *different algorithm*.

Unlike the DRC generator it cannot drive the CLI: the CLI runs the whole pipeline
(fanout, passes, the optimizer) and plan-6 ruling 2 cuts the port at step 5 of
`AutorouteConnectionRouter.route`. So it compiles and runs
`scripts/differential/java/P6T1.java` — the same driver
`scripts/differential/run.sh p6t1` diffs live against the Rust twin.

Per stem: `router.jsonl` (the driver's stdout **verbatim**, minus its `HEADER`
line), `java.log` (its stderr) and `router.meta.txt` (the jar's identity and
version, `java -version`, the hash mode, the driver path, the connection count,
the command line and the `HEADER` line, every machine-specific prefix replaced by
`<FREEROUTING_JAVA_DIR>` or `<workspace>`). The `HEADER` line is the one thing
not committed as-is: it names the jar by absolute path, byte size and mtime,
which are properties of a checkout rather than of a board.

    scripts/gen-router-reference.sh --verify-hash-modes

regenerates each stem under `-XX:hashCode=0,1,2,3,4` and requires five
byte-identical files:

    == router-rpi-splitter    5 modes agree (f4f76285affd, 8 connections)
    == router-dac2020-bm01    5 modes agree (a7a7c0dc039c, 294 connections)

This is plan-6 ruling 1's premise checked **per connection** — attempt state,

## There is no normalisation

`parity::parse_router_jsonl` parses the committed line into typed values and
`crates/fr-router/tests/reference_parity.rs` compares them rung by rung (plan-6
ruling 1: state + ripped set, then geometry, then spec §9's metrics), but nothing
is rewritten on either side. Coordinates and `traceLength` are compared as the
**strings** `Double.toString` and `java_double_to_string` produced, so no
re-parse can round a value into agreement.

## Wall clock

Quirk #162 (`SortedRoomNeighbours.calculateNewIncompleteRooms`) does not
terminate for a small fraction of room completions and neither language guards
it, so a board that reaches it hangs the JVM *and* the port. The generator bounds
itself with `timeout(1)` (`ROUTER_TIMEOUT`, default 1800 s) and reports the stem
as failed rather than hanging the machine; `run.sh p6t1` bounds both sides the
same way (`P6T1_TIMEOUT`, default 900 s). No corpus stem currently reaches it.

# Whole-board batch references (`batch.*`, Plan 7 Task 16)

`tests/reference/router-<stem>/batch.ses` is the **fourth** reference family and
the first that is a whole file the *HEAD* jar wrote: the SES of a complete
`java -jar <jar> -de <dsn> -do <ses> -mp <n>` run, byte for byte.
`batch.passes.jsonl` beside it is one JSON object per completed routing pass —
the `PassRecord` tuple `crates/fr-router/src/pipeline/stop.rs` defines.
`scripts/gen-batch-reference.sh` writes both and
`crates/fr-router/tests/batch_parity.rs` reads them.

They live in the same `router-<stem>` directories and are driven by the same
`tests/reference/router-fixtures.txt`, which gained three columns at positions
5, 6 and 7 — `max_passes|fanout|optimizer`. Fields 1-4 stay
`gen-router-reference.sh`'s; a row with `-` in `max_items` is batch-only and a
row with no `max_passes` is per-connection-only, so each script skips the other's
rows. Eight stems carry batch columns (ruling AM as amended by scan ruling 13):
four in CI, four under `FR_SLOW_PARITY=1`.

## Generated by a driver, verified against the bare jar

`P7T9.java` mode `batch`, not `java -jar … -de … -do …` directly — the
`gen-router-reference.sh` argument: it is the driver `run.sh p7t9` diffs against
the Rust twin, so the reference and the differential cannot describe different
runs. What makes the indirection safe is
`scripts/gen-batch-reference.sh --verify-driver`, which runs the **bare jar** on
the same `argv` and requires the two SES files to be byte-identical. Measured:
identical on all eight stems (3 654 / 66 387 / 15 254 / 462 / 4 509 / 56 155 /
40 915 / 212 B), and the verdict is committed into each stem's
`batch.verify-driver.txt` and appended to `batch.meta.txt`.

Mode `batch` loads through the real `management/HeadlessBoardManager` and
resolves settings through the real two-merge `SettingsMerger` ladder, because
that is what the CLI does — `applyCopperToEdgeClearanceOverride` and
`applyHoleClearanceOverride` mutate the board on 15 of the 16 corpus boards
(quirk #231), so a reference generated any other way is not the jar's output
(controller ruling AW).

## The one normalisation: quirk #92's four keyword literals

Unlike the other three families this one *has* a normalisation, and it is applied
to the **reference** side inside the test, exactly as `normalize_drc_json` is:
`parity::normalize_ses_head_tokens` rewrites `(hostCad ` → `(host_cad `,
`(hostVersion ` → `(host_version `, `(stringQuote ` → `(string_quote ` and
`(writeResolution ` → `(write_resolution `.

That is the whole set — every camelCase string literal in `SesWriter.java` and
`parser/Parser.java` combined — and it exists because this directory holds files
from **two jars**. "Why the 2.3.0 jar" above pins the port's writer to the 2.3.0
spelling, because HEAD writes Specctra it cannot read back; `batch.ses` is the
one committed file HEAD's `SesWriter` produced, so it carries HEAD's spelling of
the two such keywords an SES contains. Everything else is compared byte for byte,
and a stem that failed anywhere else would be an `XDIFF` row in
`crates/fr-router/README.md` rather than a widened normaliser.

## The budget, and the hash-mode sweep

`--verify-hash-modes` regenerates each stem's SES under `-XX:hashCode=0..4` and
requires five byte-identical files. All eight pass; the digests are in
`crates/fr-router/README.md`'s acceptance section and in each `batch.meta.txt`.

`optChangedArea`'s `TIME_LIMIT_TO_PREVENT_ENDLESS_LOOP` **cannot be disabled on
the Java side**: all four declarations are `static final int = 1000` with a
constant initialiser, so `javac` inlines them (`javap -c -p` shows `sipush 1000`
at every call site and no `getstatic`) and reflection reaches nothing. The Java
side therefore runs with the live limit and the port with
`RouterBudget::disabled()`; a byte-identical SES is *evidence* that the limit
never changed the result. The trips a run **did** take are counted from the jar's own logging: `TraceTightener.isStopRequested`
(`board/optimize/TraceTightener.java:202-211`) calls
`FRLogger.debug("TraceTightener.is_stop_requested: time limit exceeded")` on every
exceeded check, and `Log4j2ConfigurationFactory` gives the root logger `Level.ALL`
with a file appender at `DEBUG` writing to a caller-chosen path. So the count is
turning that appender on and running `grep -c`, and
`gen-batch-reference.sh --verify-driver` is what does it — on **both** the bare jar
and the driver — only after a comparison has already come back different, because
turning `DEBUG` on costs wall-clock time and wall-clock time is what the budget
measures. The driver takes the JVM system properties
`-Dfreerouting.logging.file.{location,level}` and the bare jar the program
arguments `--logging.file.{location,level}`, because `Freerouting.main`
(`Freerouting.java:1088-1098`) overwrites those properties from its own parse
before logging initialises.

(A programmatic Log4j2 counting appender was tried first and received **zero**
events against this jar's configuration factory, so the driver has no flag of its
own.)

## Wall clock

The whole eight-stem generation is ~4 min and `--verify-hash-modes` ~6 min on an
M-series laptop. The generator bounds every invocation with `timeout(1)`
(`BATCH_TIMEOUT`, default 7200 s) and is **resumable**: a stem whose `batch.ses`
and `batch.passes.jsonl` both exist is skipped unless `--force` is given.

# Whole-**program** CLI references (`cli-<stem>/*`, Plan 8 Task 6)

`tests/reference/cli-<stem>/` is the **fifth** reference family, and the only one
that is the output of a whole program rather than of a driver: what the **bare
HEAD jar** wrote for one complete command line. `scripts/gen-cli-reference.sh`
writes it from `tests/reference/cli-fixtures.txt`, and
`crates/freerouting/tests/cli_e2e.rs` reads it.

| file | what |
|---|---|
| `argv.txt` | the argv, one token per line, with `<JAVA_DIR>` and `<OUT>` placeholders so the file is the same on every machine |
| `route.ses` | the jar's SES, **verbatim** |
| `route.exit` | its exit code |
| `route.log` | its stdout followed by its stderr, machine-specific prefixes replaced |
| `manifest.json` | the manifest a **second** run with `--router.result_json=<f>` wrote |
| `meta.txt` | the jar identity, `java -version`, the hash mode, the budget note, both command lines, and the `batch.ses` cross-check verdict |

**Eleven stems**: Plan 7's eight batch stems on *the same argv*
`batch.meta.txt`'s `bare jar` line records (scan ruling R1 — the `-mp` cap is
transcribed, not invented, because a bare `router-dac2020-bm01` run is
unmeasurable, quirk #234), the two Plan 3/5 round-trip boards run **bare**, and
scan ruling R21's one qualifying board class. Four in CI, seven under
`FR_SLOW_PARITY=1` — Plan 7's split, carried over.

## The `batch.ses` cross-check

Because eight stems reuse Plan 7's argv, the generator asserts
`cli-<stem>/route.ses == <stem>/batch.ses` and records the verdict in `meta.txt`.
`gen-batch-reference.sh --verify-driver` had already proved that argv's bare-jar
output *is* `batch.ses`, so this is two references, generated by two scripts a
task apart, agreeing byte for byte. **Measured: identical on all eight.** A
mismatch is a failure, not a note.

## The budget is live, and this is the difference from Plan 7

`gen-batch-reference.sh` spends a section of its header on `optChangedArea`'s
javac-inlined 1000 ms limit and on running the port with
`RouterBudget::disabled()` against a jar that cannot switch it off. **This
generator needs none of that**: what it captures is the jar as a program, and the
port's CLI runs `RouterBudget::default()` — Java's own four literals — because
that is what a user gets. Both sides run the budget live; there is nothing to
disable on either, and no probe.

The honest cost: a live wall clock is a machine-speed dependency, so a stem whose
optimizer genuinely tripped the limit could answer different bytes on a slower
host. The bound is the `batch.ses` cross-check above, which is exactly the signal
a trip would break.

## No normalisation beyond quirk #92

`route.ses` is compared byte for byte after
`parity::normalize_ses_head_tokens` rewrites the same closed set of four
`(parser …)` keyword literals `batch.ses` needs — HEAD camelCased them while
leaving its own lexer on the snake_case tokens (Plan 3 ruling 1). Measured on
`router-rpi-splitter`: those two lines are the **only** difference between the
jar's 3 654 bytes and the port's 3 656. `route.log` goes through
`parity::normalize_log`, whose removals are listed on the function; `manifest
.json` through `parity::normalize_manifest`, whose six are listed on that one.

## Wall clock

The whole eleven-stem generation is ~6 min on an M-series laptop (each stem runs
the jar **twice** — once for the SES, once for the manifest). The generator is
**resumable**: a stem whose `route.ses` and `route.exit` both exist is skipped
unless `--force` is given, and every invocation is bounded by `timeout(1)`
(`CLI_TIMEOUT`, default 7200 s).

`Issue420-contribution-board.dsn`, the corpus's *widest* outline, was measured
and **rejected** as the R21 large-outline stem: 411 nets and 1 495 SMD pins, a
fanout stage that runs 66-119 s per pass and had not finished after ten minutes,
and a per-pin budget that is live on both sides here — a machine-speed dependency
rather than a reference. `Issue035-ReadPlaceScope.dsn` (288 290 × 101 600 DSN
units, the third-widest) is the one taken, with the optimizer off.
