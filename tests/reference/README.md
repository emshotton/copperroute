# Java reference outputs

Generated by `scripts/gen-reference.sh` from the pinned freerouting 2.3.0 jar
(the parity baseline per the Java repo's AGENTS.md). For each stem in
`fixtures.txt` the script produces:

- `<stem>/roundtrip.dsn` — Java `DsnReader.readBoard` → `DsnWriter.write`, no routing
- `<stem>/unrouted.ses`  — same board → `SesWriter.write`, no routing (0 `(wire` entries)
- `<stem>/java.log`      — driver output, for debugging

## How it works (and why not `-de/-do`)

The script compiles `scripts/gen-reference/RefWriter.java` against the jar and
runs it per fixture. The normal `-de/-do` job path was tried first and cannot
produce these references:

- `-do <file>.dsn` is accepted but the headless job writer only emits SES or
  KiCad JSON, so the DSN output is an empty file.
- `-mp 0` means *unlimited* passes, not zero.
- `--router.enabled=false` disables only the autoroute stage; fanout and the
  optimizer still run and modify the board (fanout added vias/wires).
- With all three of `--router.enabled=false --router.fanout.enabled=false
  --router.optimizer.enabled=false` the job completes with nothing to do and
  writes 0 bytes.

## Which fixtures, and why

`fixtures.txt` has seven stems. The first four (`tutorial_board`,
`Issue026-J2_reference`, `Issue103-Board-Unrouted`, `Issue143-rpi_splitter`)
are the plan's original bit-parity set. Between them they have **zero**
`polyline_path`, zero wiring `(via `, zero `(type shove_fixed|fix|protect)`
and zero `(plane ` — so they prove the `structure`/`placement`/`library`/
`part_library`/`network` writers and nothing about six others. Plan 3
controller ruling G added three more in Task 15 to close that:

| stem | exercises | roundtrip.dsn | wires in .ses |
|---|---|---|---|
| `Issue413-test` | 11 `polyline_path`, 4 wiring vias, 3 fixed states | 8,492 B | 11 |
| `Issue110-RelayModule` | 22 wiring vias, 22 fixed states | 171,349 B | 0 |
| `Issue753-CPU-85_r104` | 3 `(plane …)`, 65 `polyline_path` | 273,049 B | 0 |

`Issue413-test` is the only reference whose `unrouted.ses` carries `(wire`
entries, so it is the one that pins `SesWriter`'s trace path. The other six are
wire-free. Both halves of that are asserted: `parity_ses.rs`'s
`no_reference_contains_a_wire` runs over all six wire-free stems (the ruling-G
ones included) and `ruling_g_references_do_carry_wires` pins `Issue413-test`'s
11 entries.

**Never edit a generated file by hand** — regenerate with the script. Adding a
stem to `fixtures.txt` and re-running is the whole procedure; the script is
idempotent for the stems already present (only `java.log`'s timestamp changes).

Note the 2.3.0 jar's package layout predates the clone's renames
(`app.freerouting.board.BasicBoard`, not `board.facade`); the driver imports
the jar's names.

## Why the 2.3.0 jar, not the clone's HEAD (Plan 3 ruling 1)

The clone's HEAD camelCased fifteen Specctra keyword names in `Keyword.java`
*and* the writers' string literals (`(hostCad `, `(viaRule `, `(snapAngle `,
`(stringQuote `, ...), while its lexer still only recognises the snake_case
tokens -- so HEAD writes DSN it cannot read back (re-reading its own
`tutorial_board` output drops `host_cad`, every via rule, every clearance rule
and 26 wires). The 2.3.0 jar writes the correct Specctra tokens, and diffing
HEAD's output against these references differs in exactly those fifteen tokens
and nothing else on every fixture. The port therefore emits the 2.3.0 tokens,
these references are the acceptance target, and `docs/java-quirks.md` #92 is
the upstream bug report. Regenerating with a HEAD jar would silently move the
target; do not.

Reference files are committed. `_scratch/` holds the Rust side of a failing
comparison and is gitignored, as is `scripts/gen-reference/build/`.

Requirements: JDK 25 (`brew install openjdk@25`, then
`JAVA=/opt/homebrew/opt/openjdk@25/bin/java scripts/gen-reference.sh`), network
access on first run to download the jar into `tools/`.

# DRC references (`drc-*`, Plan 5 Task 9)

The seven stems above are `scripts/gen-reference.sh`'s. The eight `drc-*` stems are a **separate
set**, generated by `scripts/gen-drc-reference.sh` from a **different jar**, and listed in
`drc-fixtures.txt` (`stem|dsn|rules|ses`) rather than in `fixtures.txt`. Per stem:

- `<stem>/drc.json`     — the `-drc` CLI's report, **verbatim**
- `<stem>/drc.meta.txt` — the jar's path/size/mtime, its version, `java -version`, the hash mode
                          and the exact command line
- `<stem>/java.log`     — the CLI's stdout+stderr

## Why a second script and a second jar

`gen-reference.sh` is pinned to the downloaded **2.3.0** jar because the `io/specctra` byte-parity
references have to be 2.3.0's (Plan 3 ruling 10, "Why the 2.3.0 jar" above). The DRC references
have to be the clone's **HEAD** build: Plan 5 ports HEAD's `drc/**` and `io/kicad/KiCadDrc*.java`,
every file:line in that plan is HEAD's, and the two jars disagree about the report's key spelling
(HEAD writes `coordinateUnits`/`holeClearance`, 2.3.0 writes `coordinate_units`/`hole_clearance` —
plan-5 rulings 1 and 2). Putting two jars behind one `fixtures.txt` would hide that skew, so the
DRC set gets its own file, its own script and its own `drc-` stem prefix.

Unlike the DSN/SES case, no Java driver has to be compiled: `-drc` works from the CLI as-is, for a
plain DSN, for a DSN + `.rules` (`-dr`) and for a DSN + `.ses`. Driving the real CLI is also what
puts a real `qualityScore` in the reference — `DesignRulesChecker` alone never computes it
(`Freerouting.java:343-352`; plan-5 ruling 5 makes it an injected `Option<f64>` in the port, and
`crates/fr-drc/tests/reference_parity.rs` feeds the reference's own value back in).

**There is no `-ds` flag.** The session file has no option of its own: `GlobalSettings` collects
every non-`-` argument after `-de` into a slot list and sorts them by extension
(`GlobalSettings.java:564-648`), so the SES rides in the `-de` slot, joined to the DSN with `+`
(`:573-579`). `-drc` is matched by `startsWith` *before* `-dr` in the same if-chain (`:660-674`),
so the two flags cannot be confused whatever their order on the command line.

## The hash-mode sweep, and the one stem that fails it

`scripts/gen-drc-reference.sh --verify-hash-modes` regenerates every stem once per
`-XX:+UnlockExperimentalVMOptions -XX:hashCode=0,1,2,3,4` and requires the five **normalised**
documents (`scripts/normalize-drc.py`) to be byte-identical. That is what makes a reference a
property of the board rather than of the JVM run that produced it. Result on the jar named in
`drc.meta.txt`:

| stem | distinct normalised documents over 5 modes |
|---|---|
| `drc-dev-board`, `drc-bbd-mars-64`, `drc-issue593-rules`, `drc-issue593-ses`, `drc-issue753-cpu85`, `drc-issue110-relay`, `drc-tutorial-board` | **1** |
| `drc-natural-tone-preamp` | **5** — 113, 113, 114, 114, 115 violations |

`drc-natural-tone-preamp` is recorded, not papered over. `generateReport` folds
`getAllUnconnectedItems`' `track_dangling` entries into `violations`
(`DesignRulesChecker.java:271-276`), and that phase's dedup (`:160`) drops whichever dangling trace
a net entry's hash-ordered `firstItem` happens to be — a representative-dependent result
(`findRepresentativeItem`, plan-5 ruling 3; quirk #146). **All eight references are therefore
generated under `-XX:hashCode=2`**, the constant-hash mode: the only `Object.hashCode` source that
reproduces run to run and is not derived from an object address. For the seven hash-independent
stems the flag changes nothing; for this one it is what makes the reference reproducible at all.
`references_are_from_the_head_jar` asserts every `drc.meta.txt` says so.

The port's own answer on that fixture is 112 violations — its ascending-id representatives make
three of the fixture's four `Trace`-represented net entries dangling — and
`natural_tone_preamp_is_the_reference_minus_three_dangling_tracks` requires the port's document to
be this reference with exactly the three `track_dangling` entries whose item uuids are `1909`,
`1696` and `1242` deleted **in place**, pinned by uuid rather than by count. The other 44
`unconnectedItems` entries and the remaining 112 violations are byte-identical.

## The normalisation is three lines long, on purpose

`parity::normalize_drc_json` drops `date` (`ZonedDateTime.now()`, `KiCadDrcReport.java:70`, an
injected string in the port) and sorts each `unconnectedItems` entry's `items` by **numeric** uuid
(on the JVM that array is two `HashSet<Item>`s, quirk #144). It does **not** touch `violations` —
neither the array order nor any entry's `items`, because a clearance entry's `items` is
`[firstItem, secondItem]` in a deterministic order and sorting it would hide a real ordering
regression. `scripts/normalize-drc.py` is the Python twin, used by `--verify-hash-modes` only; it
is deliberately not on the path of any committed byte, which is why the committed `drc.json` is the
jar's own output and the Rust normaliser is applied to *both* sides inside the test.

## The `*-freerouting_drc.json` files in the Java fixtures directory are NOT references

`../freerouting/fixtures/Issue575-*-freerouting_drc.json` look like DRC references and are not
(plan-5 ruling 10). Verified while writing this task:

- they are `Freerouting 2.1.2-SNAPSHOT`-era and carry **no `quality_score`** key at all;
- they are snake_case, i.e. neither jar's current output for two of the type strings;
- the dev-board one claims **5 violations / 1 unconnected item** where both current jars produce
  **10 / 4**; the BBD Mars-64 one claims 93 / 0 against 96 / 3, and the Natural Tone Preamp one
  28 / 9 against 113-115 / 44.

The `*-kicad_drc.json` files beside them are KiCad 9.0.1's own output and are the evidence for
ruling 2's `DrcJsonFlavor::KiCad` spelling, not a parity target either.

**Never edit a generated file by hand** — regenerate with
`scripts/gen-drc-reference.sh [stem ...]`. The one thing that changes on every regeneration is
`date` (and `java.log`'s timestamps); the parity test drops it on both sides.
