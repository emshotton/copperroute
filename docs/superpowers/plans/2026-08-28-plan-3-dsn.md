# Plan 3 — `fr-dsn` (Specctra DSN/SES/rules reader and writer) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port freerouting's text-I/O layer — `io/specctra/**` (lexer, 30 parser scope classes, `DsnReader`, `DsnWriter`, `SesReader`, `SesWriter`, `RulesReader`, `RulesWriter`), `io/{CoordinateTransform,BoardReadResult,BoardMetadata,FileFormat}.java` and `datastructures/{IdentifierType,IndentFileWriter}.java` — as the `fr-dsn` crate, byte-for-byte identical to Java on write and item-for-item identical on read.

**Architecture:** Spec §7 (binding), §3 (parity contract), §14 (tests). `fr-dsn` sits directly on top of `fr-board`: it *builds* a `Board` through the public insert API Plan 2 delivered (`Board::new`, `insert_pin`, `insert_via`, `insert_trace_without_cleaning`, `insert_obstacle`, `insert_conduction_area`, `insert_component_outline`, …) and *reads* one back out through `get_traces`/`get_vias`/`get_connectable_items`/`items_in_board_order`. It owns no board state of its own. The Java lexer is a checked-in JFlex DFA; it is ported by transcribing its packed tables mechanically and hand-porting only the driver loop and the ~120-arm action switch (ruling 3). Java's two `static` lexer fields become instance state (a documented deviation, ruling 6). The KiCad JSON path (`io/kicad/**`, 1,574 lines) and `SessionToEagle` (627 lines) are **not** in scope — Plan 8 or later.

**Tech Stack:** Rust 2024; `fr-board` (Plan 2); `fr-geometry` (Plan 1); `thiserror`. No `serde`, no `regex`, no `tracing`.

**Spec:** `docs/superpowers/specs/2026-08-27-freerouting-rust-port-design.md` (§3, §7, §14). Also binding: `docs/plan-1-handoff.md`, `docs/plan-2-handoff.md` (rulings + the four Plan 3 obligations) and `docs/java-quirks.md`.

**Later plans:** 4 `fr-settings`, 5 `fr-drc`, 6–7 `fr-router`, 8 `fr-core` + surfaces (incl. `io/kicad`, `SessionToEagle`).

## Global Constraints

All Plan 1 and Plan 2 constraints and rulings remain in force (see `docs/plan-1-handoff.md` §Rulings and `docs/plan-2-handoff.md` §Rulings). Additionally:

Where this document quotes an expected string or number, it was taken from the Java source, from `tests/reference/`, or from a JVM run recorded in "Rulings made while writing this plan" — but the implementer re-derives it from Java and reports any disagreement rather than trusting the plan.
- **Java source authority for this plan is the clone's HEAD *except* for the fifteen `Keyword` name literals listed in ruling 1**, where the pinned 2.3.0 jar wins. See ruling 1 for the evidence; this is the single most important constraint in the plan.
- Behavioral port: reproduce Java bugs, with a `// Java bug:` marker at the site and a row in `docs/java-quirks.md`. `// totalized:` for crash→value changes (only where no reachable Java caller observes the difference — Plan 1 ruling 12), `// not ported:`, `// renamed:`, `// added in Plan N:`, `obligation:` per `docs/java-quirks.md` §Process notes. The marker's Java method name must sit on the **same line** as the marker (Plan 2 ruling 13 — `audit-port.sh` is line-based).
- No GUI, no `FRLogger`. Java's `FRLogger.warn`/`error` calls in the read path either (a) push onto `ReadScopeParameter::warnings` where Java does, or (b) vanish. They never become `tracing` calls: `fr-dsn` must not depend on `tracing`.

- `fr-dsn` depends only on `fr-board`, `fr-geometry` and `thiserror`. Any need for a fourth dependency is a ruling that must be recorded, not a silent `Cargo.toml` edit.
- Every task ends with `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, and `scripts/audit-port.sh io/specctra crates/fr-dsn/src` (plus the other three subpaths once Task 1 has extended the script) all clean, verified against the committed tree — not against a report.

## Rulings made while writing this plan (recorded here so they reach the user)

1. **The fifteen camelCased `Keyword` names at the clone's HEAD are a regression; the port emits the 2.3.0 (correct Specctra) tokens.** JVM-verified while writing this plan. HEAD's `Keyword.java` gives `AUTOROUTE_SETTINGS`, `CLEARANCE_CLASS`, `HOST_CAD`, `HOST_VERSION`, `LOGICAL_PART`, `PULL_TIGHT`, `SHOVE_FIXED`, `SNAP_ANGLE`, `START_RIPUP_COSTS`, `STRING_QUOTE`, `USE_LAYER`, `USE_VIA`, `VIA_COSTS`, `VIA_RULE`, `WRITE_RESOLUTION` the names `autorouteSettings`, `clearanceClass`, `hostCad`, `hostVersion`, `logicalPart`, `pullTight`, `shoveFixed`, `snapAngle`, `startRipupCosts`, `stringQuote`, `useLayer`, `useVia`, `viaCosts`, `viaRule`, `writeResolution`; 2.3.0 gives the snake_case Specctra tokens. The same rename leaked into **string literals in the writers** (e.g. `Parser.java:102` writes `"(stringQuote "`, `:110` `"(hostCad "`). The lexer's DFA is unchanged, so HEAD **cannot read back its own output**: re-reading HEAD's `tutorial_board` round-trip through HEAD drops `host_cad`/`host_version`, every via rule, every per-type clearance rule and 26 wires, and shifts the board bounding box. Evidence: running the existing `scripts/gen-reference/RefWriter.java` (with `board.facade.BasicBoard`) against `../freerouting/build/libs/freerouting-current-executable.jar` on all four `tests/reference` fixtures produces output whose diff against the committed 2.3.0 references is **exactly the fifteen renamed tokens and nothing else — 0 remaining diff lines on all four fixtures**. Reason: `tests/reference/` is the spec §3 acceptance target, the 2.3.0 jar is the parity baseline the Java repo's own AGENTS.md pins, and the snake_case tokens are the ones the Specctra format and every other EDA tool use. Cost if wrong: the port emits DSN no tool (including freerouting) can read, and every bit-parity test fails on 15 token names — loud and immediate, so this is a cheap ruling to get wrong in the safe direction. **Every other output-affecting difference between the two jars on the fixture corpus is zero** on the four reference fixtures; Task 15's corpus-wide differential (against the 2.3.0 jar) is the safety net for the other 101.
2. **Read lexemes and write literals are two independent tables, and neither is `Keyword.getName()` alone.** Many scopes are written as raw string literals whose text differs from the keyword's name (`Rectangle.writeScope:76` writes `"(rect "` while `Keyword.RECTANGLE.getName()` is `"rectangle"`), and the reader's lexemes come from the DFA, not from `getName()`. The port therefore keeps three things separate: the DFA's lexeme→`Keyword` mapping (Task 3, transcribed from the tables), `Keyword::name()` (Task 4, the 2.3.0 strings, used only where Java calls `getName()`), and the writers' literal strings (Tasks 11–14, transcribed one by one from each `writeScope`). Cost if wrong: a writer that emits `rectangle` instead of `rect` — caught instantly by parity, but only if the three are not conflated into one table.
3. **The lexer's DFA is ported by transcribing JFlex's packed tables, not by hand-writing a recognizer.** `SpecctraDsnStreamReader.java` is ~1,200 lines of `ZZ_CMAP_PACKED`/`ZZ_ACTION_PACKED_0`/`ZZ_ROWMAP_PACKED_0`/`ZZ_TRANS_PACKED_0`/`ZZ_ATTRIBUTE_PACKED_0` string literals plus a 240-arm `switch`. A committed one-shot generator (`scripts/gen-lexer-tables.py`) decodes the five packed strings into `src/lexer/tables.rs`; only the driver loop and the action switch are hand-ported. Reason: eight lexical states with keyword-driven `yybegin` side effects and `%ignorecase` make a hand-written recognizer a guessing game, and the `.flex` grammar in the tree (`SpecctraFileDescription.flex`, 311 lines) is the **legacy 2008 file and is not what generated this scanner** — its package is `designformats.specctra`. Cost if wrong: a hand-written lexer that is 99% right silently mis-tokenises one fixture in a hundred; the generated tables cannot.
4. **`normalize_all_traces` at the end of a DSN read runs under a `StopCheck`, and a trip produces Java's own warning string.** Quirk #76 (Plan 2 hand-off, Plan 3 obligation): a 4+-rung ladder on one net makes `PolylineTrace.split`'s entry re-walk non-terminating in Java and in the port, and `io/specctra/parser/Wiring.java:346` ends every DSN read with `board.normalizeAllTraces()`. Java already wraps that call in `try { … } catch (Exception e) { FRLogger.debug(msg); scopeParameter.warnings.add(msg); }` with `msg = "Wiring: normalization of traces failed"` (Wiring.java:345-351). The port adds `Board::normalize_all_traces_checked(&mut self, stop: StopCheck<'_>)` to `fr-board` (Task 10), consulted at the head of `split_trace`'s entry walk, in `normalize_trace`'s recursion and in each `normalize_traces` pass; `fr-dsn` passes a `TimeLimit`-backed closure (`DsnReadOptions::normalize_time_limit`, default 60 s) and, when it trips, pushes exactly that warning string and continues. Reason: it lands the divergence inside a branch Java already has, so the warning list, the board and therefore the DSN/SES output are identical for every design that does not hang, and a hanging design produces Java's own message instead of a wedged process. Cost if wrong: a slow-but-terminating board on a slow machine could trip the limit and silently under-normalise — mitigated by making the limit configurable and by asserting in Task 15 that **no fixture in the 105-file corpus trips it**.
5. **`AutorouteSettings` gets a `fr-dsn`-local `DsnRouterSettings`, not a forward reference to Plan 4's `RouterSettings`.** Java's `AutorouteSettings.readScope` returns `settings.RouterSettings` and `BoardMetadata` carries one. Plan 4 owns `fr-settings`. The port defines `DsnRouterSettings` in `fr-dsn` holding exactly the fields the DSN/rules scopes read and write (`run_router`, `run_optimizer`, `vias_allowed`, `via_costs`, `plane_via_costs`, `start_ripup_costs`, and per-layer `active`/`preferred_direction_is_horizontal`/`preferred_direction_trace_costs`/`against_preferred_direction_trace_costs`), with an `obligation:` marker naming `settings/RouterSettings.java`. Reason: Plan 4 cannot be a dependency of Plan 3 without inverting the build order in spec §15. Cost if wrong: Plan 4 has to write a `From`/`Into` pair — bounded, and the obligation is recorded on both sides.
6. **Java's two `static` lexer fields become instance state.** `SpecctraDsnStreamReader.scopeIdentifier` (used only for warning text) and `.nf` (a `NumberFormat`, not thread-safe) are `public static`. The port makes both instance fields. Reason: the plan-wide "no static mutable state" rule, and the fields are a latent data race in Java. Cost if wrong: none observable — `scopeIdentifier` only feeds messages the port drops or localises, and `nf` is a stateless parser once constructed. Recorded as a deviation with a quirks row, not as a bug fix.
7. **`PartLibrary` is ported only as far as DSN write needs.** The brief asks for a rule. `PartLibrary.java` (351 lines) reads `logical_part`/`logical_part_mapping` into `board.library.logicalParts` and pin/gate-swap data; `fr-board` already has `LogicalPart(s)`/`PartPin` (Plan 2 Task 4). The port implements `PartLibrary::read_scope` (populating `BoardLibrary::logical_parts`) and `PartLibrary::write_scope` in full, because `DsnWriter.writePcbScope` calls the latter unconditionally and a missing `(part_library …)` scope is a byte-parity failure on any fixture that has one. The **pin-swap consumers** (`Pin.swapPin`, the `was_is` scope's `changedTo` chain) are already in `fr-board`; nothing further is added. Anything in `PartLibrary.java` beyond read/write of those two scopes gets `// not ported:` with the reason. Cost if wrong: a fixture with logical parts fails byte parity in Task 11 and the gap is visible there, not later.
8. **`Circuit`/`PlaceControl`/`KiCadNetClassNames` are ported at the scope level, in full.** The survey marks them "partial", meaning Java itself only consumes part of what it parses (`Circuit` keeps min/max trace length, `PlaceControl` keeps `flip_style`/`rotate_first`). The port reproduces exactly what Java keeps and `skip_scope`s exactly what Java skips — "partial" describes Java, not a licence to skip. `KiCadNetClassNames` (45 lines) **is** in scope: `DsnReaderTest.readBoardMergesKicadDefaultIntoFreeroutingDefault` is one of the ported tests. Cost if wrong: that test fails.
9. **Bit-parity tests live in `crates/fr-dsn/tests/parity_dsn.rs`, with `parity` as a dev-dependency.** `tests/parity` is a helper library crate whose own `tests/harness.rs` tests the helpers; it has no `fr-dsn` dependency and adding one would invert the dependency direction. Cost if wrong: trivial to move.
10. **Plan 3's differential drivers link against `tools/freerouting-2.3.0.jar`, not the clone-HEAD jar Plan 2's `p2t*` drivers use.** Consequence of ruling 1: the drivers must produce the byte stream `tests/reference` holds. The 2.3.0 jar has the pre-rename layout (`app.freerouting.board.BasicBoard`, `app.freerouting.library.*`) but `app/freerouting/io/specctra/**` is already at its current package path in 2.3.0, so only the board/library imports differ from the sources being ported. `run.sh` grows a third jar mode. Cost if wrong: the drivers compare the port against a Java build the acceptance tests do not use — the exact trap ruling 1 exists to avoid.
11. **`Double.toString` is emulated as "shortest digits from Rust's `{:e}`, reformatted by Java's rules", not reimplemented from Schubfach.** Validated at plan-writing time over 600,000 doubles (200k random bit patterns, 200k `n/10^k` decimals, 200k integers; seed 42) against JDK 25's `Double.toString`, using Python's `repr` as a stand-in for Rust's shortest-digit output: **0 mismatches**. Reason: JDK 19+ (`Double.toString` spec since JDK-4511638) and Rust's `{}`/`{:e}` both promise the shortest decimal that round-trips, closest to the value; only the *presentation* differs (Rust drops the `.0`, never uses `E` notation, prints `-0`). Cost if wrong: Rust's tie-breaking could differ from Java's in a case the 600k sample missed — which is precisely why Task 2 ships a dedicated `p3t2` differential driver that must run at least 10 M doubles clean before the task closes, rather than trusting this experiment.

### Task 2: Java number formatting — `Double.toString`, `Float.toString`, rotation format, `p3t2` differential

**Files:** `crates/fr-dsn/src/format/double.rs`; `crates/fr-dsn/tests/number_format.rs`; `scripts/differential/java/P3T2.java`, `scripts/differential/rust/src/bin/p3t2.rs`, `scripts/differential/run.sh` (add `p3t2`, add `-Djava.awt.headless=true` to every `java` invocation, unpin `JAVA25_HOME` to `/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home`), `scripts/differential/README.md`.
**Java:** `java.lang.Double.toString` / `Float.toString` (JDK 19+ spec), `io/specctra/parser/{Wiring.java:97, PolygonPath.java:27,31,33, Rectangle.java:76-82, Circle.java, Polygon.java}` (the `String.valueOf(double)` sites), `io/specctra/parser/AutorouteSettings.java:228,234` (`String.valueOf((float) …)` — **`Float.toString`**, a different algorithm), `io/specctra/SesWriter.java:259-269` (`formatPlacementRotation`), `geometry/planar/Limits`-side `java_round` (already in `fr-geometry`).

**Interfaces produced:**
- `pub fn java_double_to_string(d: f64) -> String`. Algorithm (ruling 11):
  1. `NaN` → `"NaN"`; `+∞` → `"Infinity"`; `-∞` → `"-Infinity"`; `±0.0` → `"0.0"`/`"-0.0"` (sign from the **sign bit**, so `-0.0` is negative).
  2. Take `m = d.abs()`. Get shortest round-trip digits and decimal exponent from `format!("{:e}", m)` — Rust's `LowerExp` yields `D[.DDD]e<exp>` with no `+` and no leading zeros. Let `digits` be the significand with the point removed and trailing zeros stripped (never empty; `"0"` only for zero, handled above) and `exp10` the exponent of the leading digit.
  3. If `-3 <= exp10 <= 6` (equivalent to Java's `10^-3 <= m < 10^7` because `10^exp10 <= m < 10^(exp10+1)`), emit plain decimal with **at least one digit either side of the point**: integer part `digits[..=exp10]` right-padded with `0`s when `exp10 >= digits.len()`, fraction part the remainder or `"0"`; for `exp10 < 0` the integer part is `"0"` and the fraction is `-exp10-1` zeros then `digits`.
  4. Otherwise emit `D "." (rest or "0") "E" exp10` — computerized scientific notation, uppercase `E`, no `+` on a positive exponent.
  5. Prefix `-` when negative.
- `pub fn java_float_to_string(f: f32) -> String` — the same shape on `f32`, with `{:e}` on the `f32` (shortest round-trip *for a float*, which is a different digit count from the `f64` widening — do **not** widen and reuse the `f64` path).

### Task 14: `RulesReader` and `RulesWriter`, and the `ViaInfoId` renumbering obligation

- **`apply_via_info` (RulesReader.java:340-350) is the Plan 2 obligation.** Java does `ViaInfo existing = viaInfos.get(name); if (existing != null) viaInfos.remove(existing); viaInfos.add(viaInfo);`. Java's `ViaRule`s hold `ViaInfo` **object references**, so the removal disturbs no rule — but it *does* move the entry to the tail of a `Vector`, and `ViaInfos` iteration order is what the DSN and rules writers emit, so the reordering **is** observable. This port's `ViaRule`s hold `ViaInfoId` indices (`crates/fr-board/src/rules/via.rs`), so a naive remove+add silently re-points every later rule. Implement the renumbering as `BoardRules::replace_via_info_renumbering_rules(&mut self, old_id: ViaInfoId, new_info: ViaInfo) -> ViaInfoId` in `fr-board` next to `ViaInfos::remove`'s existing obligation doc comment, so the hazard and its fix live together; tick the obligation in `docs/plan-2-handoff.md`.
- `pub fn write(board: &Board, out: &mut impl Write, design_name: &str, settings: Option<&DsnRouterSettings>) -> io::Result<()>` — RulesWriter.java:57ff: `(rules PCB <designName>` where the design name is written with **raw `file.write`, not `identifier_type.write`**, so it is never quoted (asymmetric with `DsnWriter`, which quotes it — `// Java bug:` + quirks row).
