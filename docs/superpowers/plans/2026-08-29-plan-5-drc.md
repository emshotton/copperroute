# Plan 5 — `fr-drc` (`DesignRulesChecker`, the ratsnest, and the KiCad DRC JSON report) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port freerouting's design-rule checker — `drc/{DesignRulesChecker,ClearanceViolation,NetIncompletes,AirLine,UnconnectedItems}.java`, the four `io/kicad/KiCadDrc*.java` report DTOs, `core/scoring/BoardStatisticsClearanceViolations.java`, and the item-level clearance compute `Item.clearanceViolations`/`clearanceViolationCount`/`calculateClearanceBetweenTwoShapes` with `Via`'s override — as the `fr-drc` crate plus four new methods on `fr-board`, producing the same clearance-violation list, the same unconnected-item list, the same incomplete counts and the same KiCad DRC JSON as Java's `-drc` mode, byte for byte after the documented normalisation.

**Architecture:** Spec §8 (binding for the surface), §3 (the DRC violation list is a *bit-parity* acceptance), §14.2 (references generated from the Java jar). `fr-drc` sits on `fr-board` and `fr-dsn`: it borrows a `&mut fr_board::Board` (ruling 8), takes an `fr_dsn::CoordinateTransform` as a **parameter** (Plan 3 ruling A left the transform in `fr-dsn`, and `fr-drc` may depend on `fr-dsn` — ruling 7), and writes its JSON through the Gson-compatible formatter Plan 4 built, which Task 1 moves down into `fr-dsn::format::json` so both crates share one copy. Four methods land in `fr-board` rather than `fr-drc` because they are `Item` methods in Java and the Plan 2 hand-off left `// added in Plan 5:` markers at their sites (`crates/fr-board/src/items/mod.rs:65`, `crates/fr-board/src/board/connectivity.rs:1060-1065`).

**Tech Stack:** Rust 2024; `fr-board` (Plan 2); `fr-dsn` (Plan 3); `fr-geometry` (Plan 1); `serde` + `serde_json`; `thiserror`. **No `fr-settings` dependency** (ruling 12), no `chrono`/clock crate (ruling 5), no `tracing`, no static mutable state.

**Spec:** `docs/superpowers/specs/2026-08-27-freerouting-rust-port-design.md` (§2, §3, §4, §8, §14, §15). Also binding: `docs/plan-2-handoff.md` (§Obligations → Plan 5), `docs/plan-3-handoff.md` (§Plan 5), `docs/plan-4-handoff.md` (§Plan 5), `docs/java-quirks.md`.

**Later plans:** 6–7 `fr-router`, 8 `fr-core` + surfaces (CLI `-drc` plumbing, KiCad board JSON, MCP `check_drc`).

> ### ⚠ Two of this plan's three outputs are bit-parity; the third is not — read rulings 3 and 4 first
>
> The **clearance-violation list** and the **`violations` array of the report** are byte-identical across JVM runs and across `-XX:hashCode` modes: JVM-verified while writing this plan (ruling 3's probe). They are the spec §3 bit-parity surface and this plan's hard acceptance.
>
> The **`unconnectedItems[].items` arrays** and the **airline endpoints** are *not*. Both are ordered by `HashSet<Item>` iteration over objects with no `hashCode` override, i.e. by JVM identity hash. Running the HEAD jar under `-XX:hashCode=0..4` on `Issue575-drc_dev-board_4_hole_clearance_violations.dsn` produces five different `items` orders and five different airline endpoint sets, while **every count stays identical** (`incompleteCount=9`, `violations=2`, `maxConnections=96` in all five). Java has no order here to port. Ruling 3 defines the port's order; ruling 4 scopes the airline parity to counts. A plan that treats either as bit-parity will chase a difference that does not exist in Java.

## Rulings made while writing this plan (recorded here so they reach the user)

1. **Parity target is the clone's HEAD jar (`Freerouting 2.3.1-SNAPSHOT`), and HEAD's camelCase drift from the schema it names is recorded as a Java bug.**
   Both jars were run on `Issue575-drc_dev-board_4_hole_clearance_violations.dsn` while writing this plan (`-Djava.awt.headless=true -Duser.language=en -Duser.country=US`, `-de <dsn> -drc <out>`):
   - HEAD top-level keys: `$schema, coordinateUnits, date, kicadVersion, freeroutingVersion, source, unconnectedItems, violations, schematicParity, qualityScore`; violation `type`s `holeClearance`, `track_dangling`.
   - 2.3.0 top-level keys: `$schema, coordinate_units, date, kicad_version, freerouting_version, source, unconnected_items, violations, schematic_parity, quality_score`; violation `type`s `hole_clearance`, `track_dangling`.
   - **Everything else is identical**: 10 violations, 4 unconnected entries, the same descriptions, the same `pos` values, the same uuids, the same order, the same `quality_score` `902.078369140625`.
   `$schema` points at `https://schemas.kicad.org/drc.v1.json`, and the real KiCad output in `../freerouting/fixtures/*-kicad_drc.json` (KiCad 9.0.1) uses **snake_case** — so 2.3.0 matched the schema its own `$schema` names and HEAD does not. The port emits HEAD's spelling by default (parity) with a `// Java bug:` marker on the key table and quirks row #143. *Reason:* the ported sources are HEAD's, every file:line in this plan is HEAD's, and HEAD's own test asserts camelCase (`DesignRulesCheckerTest.java:88-96`); pinning references from 2.3.0 would put an invisible skew into every DRC parity test. *Cost if wrong:* if upstream reverts to snake_case, ruling 2's flavor table makes it a one-line default change instead of a re-baseline.
2. **Two schema flavors, one key table, both tested.** `DrcJsonFlavor::{FreeroutingHead, KiCad}`. `FreeroutingHead` is the parity default and emits ruling 1's camelCase plus `holeClearance`/`unconnectedItems`; `KiCad` emits `coordinate_units`/`kicad_version`/`freerouting_version`/`unconnected_items`/`schematic_parity`/`quality_score` plus `hole_clearance`/`unconnected_items` — i.e. exactly 2.3.0's output, which is also the real KiCad spelling. `$schema`, `date`, `source`, `violations` and the per-violation/per-item keys are the same in both. One `const KEYS: [FlavorKeys; 2]` table, one serialiser, two golden tests. **Which flavor the CLI defaults to is a product decision and is Plan 8's** — recorded as an obligation, not decided here. *Reason:* the difference is nine strings; carrying both costs one table and removes a future re-baseline. *Cost if wrong:* nil — the second flavor is dead code Plan 8 either wires or deletes.
3. **Determinism where Java has none: `HashSet<Item>` order becomes ascending item id, everywhere.** Java's `DesignRulesChecker.getAllUnconnectedItems` builds `connectedSets` as `HashSet<Item>` (`:118`) and `NetIncompletes.calculateNetItems` iterates `HashSet<Item>` (`:295,:299`); `Item` has no `hashCode` override, so both are identity-hash ordered. **JVM-verified while writing this plan**: five runs of the HEAD jar under `-XX:+UnlockExperimentalVMOptions -XX:hashCode=0..4` on the dev-board fixture give five different `unconnectedItems[0].items` orders (`['775','771','762','70','42','786']` for `hashCode=0`, `['815','814','787','786','785','784']` for `hashCode=3`, …), and — after stripping `date` and sorting each `items` array by numeric uuid — the five documents are **byte-identical**. The port therefore fixes, as a deliberate divergence:
   - `unconnectedItems[].items` — ascending item id;
   - the seed order of `calculateNetItems`' outer loop — ascending item id;
   - `itemsByNet` — a `BTreeMap<i32, Vec<ItemId>>`, i.e. ascending **net number** (Java's `HashMap` iteration coincides with this for every net number below the table size, which is every fixture in the corpus);
   - `findRepresentativeItem` — the lowest-id `Pin`, else the lowest-id `Trace`, else the lowest-id item (Java takes *a* Pin, not a particular one; this is observable, because the representative's description goes into the `description` string).
   Quirks row #144, and the parity harness normalises by sorting `items` arrays before comparing. *Reason:* there is no Java order to copy, and the port's own §3 requirement is "deterministic run-to-run". *Cost if wrong:* a reference generated on one JVM would not match another; the normaliser is what makes the reference portable, and Task 9 proves it by generating under all five hash modes and requiring one file.
4. **The airline *list* is not a parity surface; the airline *counts* are. (This corrects the survey, which called `getAllAirlines` "deterministic".)** `getAllAirlines` is deterministic in its *flattening* (net-number ascending, `LinkedList` order within a net), but the airlines themselves come out of a Delaunay triangulation whose corner-insertion order is `calculateNetItems`' `HashSet` order. Measured with a purpose-built probe against the HEAD jar (`Probe.java`: `calculateAllIncompletes` → `maxConnections`, `getIncompleteCount`, `getAllAirlines`, `getAllClearanceViolations().size()`), under `-XX:hashCode=0,1,2,3,4`:

   | fixture | maxConnections | incompleteCount | violations | sorted airline `(net,from,to)` list |
   |---|---|---|---|---|
   | `Issue575-drc_dev-board_4_hole_clearance_violations` | 96 | 9 | 2 | **5 different digests** |
   | `Issue575-drc_BBD_Mars-64_6_track_1_hole…` | 106 | 3 | 76 | 2 different digests over 3 modes |
   | `Issue575-drc_Natural_Tone_Preamp_7_unconnected_items` | 218 | 145 | 0 | 3 different digests over 3 modes |

   So `maxConnections`, `getIncompleteCount()`, the per-net counts and the violation list are **hash-independent** and are parity; the endpoints of each airline are **hash-dependent** and are not. The `p5t2` differential compares counts strictly and the endpoint list *informationally* (printed, diffed, and any difference classified against this table rather than treated as a failure). *Reason:* the alternative is to declare a port bug every time the port's ascending-id seed order picks a different equal-length Delaunay edge than a particular JVM run did. *Cost if wrong:* a real ratsnest bug could hide behind "expected diff" — mitigated by the counts being strict, by quirk #82 being unfixed (so the port's triangulation is the same algorithm), and by `p5t2` printing the *count* of endpoint differences so a regression from 3 to 300 is visible.
5. **`date`, `source`, `freerouting_version` and `qualityScore` are all injected; `fr-drc` has no clock and no `BoardStatistics`.** `DrcReportOptions { source, coordinate_unit, date, freerouting_version, quality_score: Option<f64> }`. Java's `ZonedDateTime.now().format(ISO_OFFSET_DATE_TIME)` (`KiCadDrcReport.java:70`) is a constructor side effect that makes the class untestable; the port takes the formatted string. `qualityScore` is `(double) finalStats.getNormalizedScore(routerSettings.scoring)` (`Freerouting.java:349`) — a `float` widened to `double`, hence the `.078369140625` tails — and `getNormalizedScore` needs `BoardStatistics`' trace lengths, via counts and bend counts (`BoardStatistics.java:600-620`), which spec §4 puts in `fr-core` (**Plan 8**). So it stays an `Option<f64>` parameter: `None` omits the key exactly as Gson omits a null `Double` (verified: `DesignRulesCheckerTest`'s `generateReportJson` path emits no `qualityScore`). Plan 5 ports only the DRC-side inputs to the score: `BoardStatisticsClearanceViolations` (Task 6) and `maxConnections`/`incompleteCount`. *Reason:* a clock in a parity crate is a permanent flake, and pulling `BoardStatistics` forward would drag the whole scoring stack into Plan 5. *Cost if wrong:* Plan 8 has to thread one more parameter; the hand-off names the call site.
6. **Every `%.4f` is emitted with `.` unconditionally, and the reference generator pins the locale.** `String.formatted` uses the default `FORMAT` locale, so a German JVM writes `expected: 0,0500 mm` (JVM-verified in the survey). The port formats with `fr_dsn::format::double::java_format_fixed(x, 4)`, which is locale-free, and `scripts/gen-drc-reference.sh` passes `-Duser.language=en -Duser.country=US`. Quirks row #145 records that Java's output is locale-dependent and the port's is not. *Cost if wrong:* a reference generated on a comma-locale machine would fail everywhere else; the generator's flag is the fix and Task 9 asserts no description contains a `,`-decimal.
7. **`fr-drc` may depend on `fr-dsn`, and Plan 4's Gson formatter moves down into `fr-dsn::format::json`.** Spec §4's dependency line is `fr-router → fr-drc → fr-board`, with `fr-dsn` a sibling; but `CoordinateTransform` lives in `fr-dsn` (Plan 3 ruling A), the report's floats need `java_double_to_string`, and the report's JSON needs Plan 4's `JavaNumberFormatter`. `fr-drc → fr-dsn → fr-board → fr-geometry` stays strict and acyclic. Rather than a second copy of the formatter, **Task 1 moves `crates/fr-settings/src/json.rs`'s private `JavaNumberFormatter` into `crates/fr-dsn/src/format/json.rs` as a `pub struct`**, re-exported from `fr_dsn::format`; `fr-settings` keeps its two entry points and its whole test file unchanged, which is the guard that the move is behaviour-preserving. `fr-drc` does **not** depend on `fr-settings`. *Reason:* two copies of a byte-parity formatter is two chances to drift, and `fr-dsn` is the crate that already owns Java number rendering. *Cost if wrong:* the move is mechanical and `cargo test -p fr-settings --test json` fails loudly if it is not.
8. **The four `fr-board` additions take `&mut self`, and `DesignRulesChecker` borrows `&mut Board` — a deliberate widening of the brief's `&Board`.** `Item.clearanceViolations` has **two** side effects in Java: it lowers `this.smallestClearance` (`Item.java:451-453`) and it advances the static `ShapeSearchTree.lastGeneratedEntryId` through every tree query (`ShapeSearchTree.java:55`, which the port made a `SearchTreeManager` field, reached through `entry_counter_mut`). `crates/fr-board/src/items/header.rs:125` already carries `pub smallest_clearance: f64` for exactly this. Hiding either behind interior mutability would make quirk #153 ("`smallestClearance` is never reset") invisible and would fork `SearchTreeManager`'s existing counter protocol. So:
   ```rust
   impl Board { pub fn clearance_violations(&mut self, id: ItemId) -> Vec<ClearanceViolation>; }
   pub struct DesignRulesChecker<'a> { board: &'a mut Board, … }
   ```
   `generate_report` and `report_to_json` are `&mut self` on the checker for the same reason (they call `get_all_clearance_violations` internally, `DesignRulesChecker.java:216`). *Reason:* Java's method mutates two things and the port should say so in its type. *Cost if wrong:* Plan 8's `-drc` path owns the board and can lend it mutably; the MCP `check_drc` tool likewise. If a later caller genuinely needs `&Board`, the fix is a `Cell<u64>` counter — a contained change the hand-off names.
9. **`ClearanceViolation` is defined in `fr-board`, in `items/clearance_violation.rs`.** `Item.clearanceViolations` returns it, and `fr-board` cannot depend upward on `fr-drc`. It carries `first_item: ItemId`, `second_item: ItemId`, `shape: TileShape`, `layer: usize`, `expected_clearance: f64`, `actual_clearance: f64` — ids, not references, per `global-constraints.md`'s no-back-pointer rule. `fr-drc` re-exports it so `fr_drc::ClearanceViolation` is the name callers use. The two headless statics `aggregateSortedBySeverity`/`smallestClearance` (`ClearanceViolation.java:64-75, :86-94`) have a ported test caller (`RatsnestClearanceHeadlessTest`), so they become `Board::aggregate_violations_sorted_by_severity` / `Board::smallest_clearance`; `printInfo` (`:96-121`) is `// not ported:` (GUI/`TextManager`).
10. **Reference generation is a sibling script driving the real `-drc` CLI, not an extension of `gen-reference.sh` and not a bespoke driver.** `scripts/gen-reference.sh` is pinned to the 2.3.0 jar because it produces the `io/specctra` byte-parity references (Plan 3 ruling 10); this plan's references need the **HEAD** jar (ruling 1), so mixing the two into one script would put two jars behind one `fixtures.txt`. And unlike the DSN/SES case — where the `-de/-do` job path could not write DSN headlessly and `RefWriter.java` was necessary — `-drc` **works from the CLI as-is**, verified while writing this plan for a plain DSN, for a DSN + `.rules` (`-dr`), and for a DSN + SES (`-de "<dsn>+<ses>"`; note the SES goes in the `-de` slot list, **not** `-do`, which is the output file — a `-do` SES changes nothing in the report). Driving the real CLI also gets `qualityScore` for free, which a `DesignRulesChecker`-only driver would not produce. So: `scripts/gen-drc-reference.sh` + `tests/reference/drc-fixtures.txt`, writing `tests/reference/<stem>/drc.json` (normalised) and `drc.meta.txt` (jar path, mtime, `java -version`). **The `../freerouting/fixtures/*-freerouting_drc.json` files are NOT references**: they are `Freerouting 2.1.2-SNAPSHOT`-era, carry no `quality_score`, and the dev-board one claims 5 violations / 1 unconnected where both current jars produce 10 / 4. Task 9 records that in `tests/reference/README.md`.
11. **The two count families in the Java tests measure different things, and both are ported.** `KiCadDrcViolationRoutingTest` asserts `BoardStatistics.clearanceViolations.totalCount` and `connections.incompleteCount`; the report's arrays are longer. Measured on the HEAD jar while writing this plan:

    | fixture | `clearanceViolations.totalCount` | report `violations` | breakdown | `incompleteCount` | report `unconnectedItems` |
    |---|---|---|---|---|---|
    | `…dev-board_4_hole_clearance_violations` | **2** | 10 | 2 `holeClearance` + 8 `track_dangling` | **9** | 4 |
    | `…BBD_Mars-64_6_track_1_hole…` | **76** | 96 | 64 `holeClearance` + 12 `clearance` + 18 `via_dangling` + 2 `track_dangling` | **3** | 3 |
    | `…Natural_Tone_Preamp_7_unconnected_items` | **0** | 114 | 110 `track_dangling` + 4 `via_dangling` | **145** | 44 |

    The reconciliation is exact and mechanical: `report.violations` = the deduplicated clearance list **plus** the `track_dangling`/`via_dangling` entries `generateReport` moves out of `getAllUnconnectedItems` (`DesignRulesChecker.java:268-276`); `report.unconnectedItems` = one entry per net with ≥2 connected sets, while `incompleteCount` = the number of *airlines* (Σ (groups − 1) per net), which the Java test's own comment explains (`KiCadDrcViolationRoutingTest.java:41-48`). The survey's "dev-board gives 10/4 via the report" and the test's "9/2" are therefore both right and measure different quantities. The port pins **all six numbers per fixture**, including the third row the survey omitted. *Cost if wrong:* nil — every number above is a measurement, not an inference.
12. **`DesignRulesCheckerSettings` is not a parameter of the port's checker.** Java's field is stored and never read (`DesignRulesChecker.java:32,44`); 10 of its 15 constructions pass `null`, including both `BoardStatistics` call sites (`:268,:339`) and every `autoroute/pipeline/*`; `includeWarnings`/`includeErrors` filter nothing. Taking it would force `fr-drc → fr-settings` for a dead field. The port drops the parameter with `// not ported: DesignRulesChecker.drcSettings` naming the two lines and the reason, and Plan 4's quirk #115 (a primitive `boolean` `false` is unmergeable) is cross-referenced from there. *Cost if wrong:* if a later upstream release reads the field, `fr-drc` gains one dependency and one parameter.
13. **Scope: `-drc` plumbing, KiCad JSON session input, and `BoardComparator` are all out.** `Freerouting.initializeDrc` (`Freerouting.java:246-372`) — the `-de`/`-dr` slot handling, the `.json`-vs-`.ses` session branch (`:296-329`), `coordinateUnit = "mm"` hard-coded (`:335`), `sourceFileName` basename (`:339`), the quality-score merge (`:343-352`) and the write-or-stdout choice (`:357-370`) — is **Plan 8's**, and this plan's public surface is exactly what Plan 8 will call. `io/kicad/{KiCadJsonReader (1011 loc), KiCadJsonWriter (227), KiCadBoardJson}` are `// added in Plan 8:` lines in the audit map. `board/state/BoardComparator.java`, whose `// added in Plan 5:` marker sits at `crates/fr-board/src/board/mod.rs:57`, is **not needed by the DRC layer** — nothing in `drc/**` or the `-drc` path references it — so Task 12 rewrites that marker to `// added in Plan 8: board/state/BoardComparator.java …` with the reason (it belongs to the result-manifest/report layer, spec §10), rather than porting it here. *Cost if wrong:* one marker moves again.
14. **The differential is two drivers, not one.** `p5t1` is report-level: Java `DesignRulesChecker.generateReport` → `GsonProvider.GSON.toJson` vs the port's `report_to_json(FreeroutingHead)`, both normalised, over every `.dsn` in `../freerouting/fixtures` that reads `Success` (105 files). `p5t2` is algorithm-level: the raw violation list (`id1,id2,layer,expected,actual`), the unconnected list (`type,firstId,secondId,itemIds`), the airline list (`net,fromId,toId`) and the three counters, so a report match cannot mask a compensating pair of errors. Ruling 4's expected-diff class applies to `p5t2`'s airline block only. *Cost if wrong:* a report-only differential would pass on a board where the port picks different violations that render identically — implausible but unfalsifiable without `p5t2`.
15. **Within one connected set the iteration order is Java-determined and must be reproduced descending. (This corrects the survey, which attributed all of `calculateNetItems`' order to the `HashSet`.)** `Item.getConnectedSet` returns a **`TreeSet<Item>`** (`Item.java:606`), and `Item.compareTo`'s subtraction is reversed (`Item.java:95-103`, quirk #44), so a connected set iterates **descending item id**. `NetIncompletes.calculateNetItems` (`:293-322`) builds `itemsInComponent` by walking that `TreeSet`, so the order *within* one component is deterministic and descending; only the choice of the next seed (`uniqueItems.iterator().next()`, `:298`) is hash-ordered. The port's `Board::connected_set` returns a `BTreeSet<ItemId>` (**ascending**), so every DRC walk of a connected set must iterate `.rev()`. Ruling 3's free choice covers the seed order only. *Reason:* getting this backwards silently reverses the Delaunay insertion order inside every component, changing which equal-length edges the ratsnest picks — a wrong-output bug with no crash. *Cost if wrong:* caught by Task 5's `net_items_are_ordered_descending_within_a_component` test and by `p5t2`'s airline-difference count jumping.
