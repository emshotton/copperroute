# Net Ties Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Import, route and DRC-check `.kicad_pcb` boards whose footprints carry `net_tie_pad_groups`, with the deliberate short exempt and every other short still reported.

**Architecture:** A net tie pad keeps its own single net, so nothing gains permission to land on it. A new `NetTies` registry on `BoardRules` records, per pad item, the footprint it came from and the netcodes it may short with — the analogue of KiCad's `FOOTPRINT::GetNetTieCache`. Two registered pads of one footprint stop being obstacles to each other in `Item::is_obstacle`, and `copper-drc`'s `pair_clearance` returns 0 for the same pair, which is exactly what KiCad's `DRC_ENGINE::EvalRules` does. The copper graphic that joins the pads is given both nets, which makes it transparent to them and opaque to everything else without any new predicate.

**Tech Stack:** Rust 2024 edition, workspace crates `copper-board`, `copper-dsn`, `copper-drc`; `cargo nextest` for tests; plain JavaScript for `web/kicad.js`; the `benchmark` suite (uv + `kicad-cli`) for acceptance.

**Spec:** `docs/superpowers/specs/2026-09-15-net-ties-design.md`

## Global Constraints

- Comments are for unexpected behaviour only. Do not write comments that restate the code, describe past or future states, or cite this plan, the spec, tickets or tasks (`CLAUDE.md`, `CONTRIBUTING.md`).
- `web/kicad.js` and `crates/copper-dsn/src/kicad/pcb/` must emit byte-identical `KiCadBoardJson`. `crates/copper-dsn/tests/kicad_pcb_parity.rs` enforces this; a new DTO field must be emitted by both or by neither.

- Field names in `dto.rs` are camelCase to match the KiCad JSON, and the file carries `#![allow(non_snake_case)]` conventions already in use — follow the surrounding style rather than renaming.
- Run tests with `cargo nextest run -p <crate>` (or `cargo test -p <crate> --test <file>` when nextest is unavailable). The full gate is `cargo nextest run --workspace`.
- Boards with no net tie must be unaffected: `NetTies` is empty and every query short-circuits on `is_empty()`.

```rust
use std::collections::HashMap;

use crate::ids::ItemId;

#[derive(Debug, Clone, PartialEq, Eq)]
struct NetTiePad {
    footprint: String,
    nets: Vec<i32>,
}

#[derive(Debug, Clone, PartialEq, Eq, Default)]
pub struct NetTies {
    pads: HashMap<ItemId, NetTiePad>,
    by_footprint: HashMap<String, Vec<ItemId>>,
}

impl NetTies {
    pub fn register_pad(&mut self, pad: ItemId, footprint: String, nets: Vec<i32>) {
        self.by_footprint
            .entry(footprint.clone())
            .or_default()
            .push(pad);
        self.pads.insert(pad, NetTiePad { footprint, nets });
    }

    #[must_use]
    pub fn is_empty(&self) -> bool {
        self.pads.is_empty()
    }

    #[must_use]
    pub fn pads_of(&self, footprint: &str) -> &[ItemId] {
        self.by_footprint
            .get(footprint)
            .map_or(&[][..], Vec::as_slice)
    }

    #[must_use]
    pub fn nets_of(&self, pad: ItemId) -> &[i32] {
        self.pads.get(&pad).map_or(&[][..], |p| p.nets.as_slice())
    }

    #[must_use]
    pub fn may_short(&self, a: ItemId, a_nets: &[i32], b: ItemId, b_nets: &[i32]) -> bool {
        if self.pads.is_empty() {
            return false;
        }
        let (Some(pad_a), Some(pad_b)) = (self.pads.get(&a), self.pads.get(&b)) else {
            return false;
        };
        pad_a.footprint == pad_b.footprint
            && b_nets.iter().any(|net| pad_a.nets.contains(net))
            && a_nets.iter().any(|net| pad_b.nets.contains(net))
    }
}
```

Register the module in `crates/copper-board/src/rules/mod.rs` by adding `pub mod net_ties;` to the module list and `pub use net_ties::NetTies;` to the re-exports, both in alphabetical position.

fn board_of(text: &str) -> Board {
    let imported = read_pcb(text, "tie", &default_net_class()).expect("the board imports");
    match read_board_json(imported.board, None) {
        BoardReadResult::Success { board: Some(b), .. } => *b,
        other => panic!("expected a loaded board, got {other:?}"),
    }
}

fn pins(board: &Board) -> Vec<copper_board::ItemId> {
    let mut ids: Vec<_> = board
        .items
        .iter()
        .filter(|(_, item)| matches!(item, Item::Pin(_)))
        .map(|(id, _)| *id)
        .collect();
    ids.sort();
    ids
}

#[test]
fn a_tie_boards_pads_are_registered_against_each_others_nets() {

fn conduction_nets(board: &Board) -> Vec<Vec<i32>> {
    let mut areas: Vec<(copper_board::ItemId, Vec<i32>)> = board
        .items
        .iter()
        .filter(|(_, item)| matches!(item, Item::ConductionArea(_)))
        .map(|(id, item)| {
            let mut nets = item.net_nos().to_vec();
            nets.sort();
            (*id, nets)
        })
        .collect();
    areas.sort_by_key(|(id, _)| *id);
    areas.into_iter().map(|(_, nets)| nets).collect()
}

pub fn pair_clearance(
    board: &Board,
    constraints: &DrcConstraints,
    a: &Item,
    b: &Item,

    if board
        .rules
        .net_ties

    .into_iter()
    .flatten()
    .max()
}

## Notes for the implementer

**Read before Task 5.** The spec's open question is `FOOTPRINT::BuildNetTieCache` in KiCad's `pcbnew/footprint.cpp`: how it assigns netcodes to a footprint's *graphics*, which this plan implements as "the nets of every tie group whose pad the graphic intersects". Read that function and adjust Task 5 if it disagrees. The rule it must match is the one `DRC_ENGINE::EvalRules` consumes in `pcbnew/drc/drc_engine.cpp`, under the comment "Handle Footprint net ties".

**Why the DRC change is so small.** Tie copper carries both nets, so `same_defined_net` in `checks/copper.rs:19` already sees a shared net between the joining copper and a trace on either net. Only the pad-versus-pad case needs `pair_clearance`. Resist adding a second predicate in `copper.rs` — if a case is not covered, first check whether the item's `net_nos` is what you expect.

**Why hole clearance is not exempt.** KiCad zeroes only the clearance constraint; `checks/copper.rs:235` runs its hole section after the clearance block returns, and must keep running for tie pads.
